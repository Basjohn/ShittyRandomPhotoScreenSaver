- **Final resolved state:** the attempted active-transition pending-paint requeue guard was removed, and its parser signature remains as a red regression bar. Production must keep strict update coalescing rather than queueing extra UI work to force transition cadence.
- **Follow-up evidence:** after removing the requeue behavior, the latest `--perf` parser run still reports paired paint-delivery starvation (`GL RENDER` healthy while same-screen `GL PAINT` collapses), with no pending-paint requeues, no shader fallbacks, and no cache worker fallbacks. That proves the requeue was a harmful anti-pattern, not the root cause; the active root-cause work is paint/event-loop delivery starvation, settings/display lifecycle stalls, slow uploads, and visualizer tick cadence.
- **Observed failure pattern:**
  - a bounded "rescue" was added to request another transition frame when a pending paint looked stale
  - the latest `--perf` run became materially worse, with the parser reporting `134` pending-paint requeue rescues
  - high-refresh paint cadence still collapsed into suspicious near-60 / divisor-like windows, so the extra UI work increased churn without solving delivery
- **Root cause of the regression:**
  1. The change treated missed/late paint delivery as something to overpower with more queued UI work.
  2. SRPSS already has a fragile UI thread under settings, widget, GL upload, visualizer tick, and transition pressure.
  3. The rescue path became another producer of UI pressure instead of identifying the owner that was starving paint delivery.
- **What fixed the regression:**
  - removed the runtime requeue behavior from `rendering/adaptive_timer.py`
  - kept parser detection of `[PERF] [GL RENDER] Pending paint update exceeded coalescing window` as a red bar so this failed pattern cannot return silently
  - added an adaptive-timer regression test proving stale transition pending dispatches do not requeue
- **Guardrail lesson:**
  - UI pressure is never the default answer to perf/cadence bugs in SRPSS
  - do not fix FPS, missed paints, timer starvation, or visualizer latency with repaint/update loops, rescue timers, broad refreshes, or extra UI-thread work
  - first prove the ownership/timing/cache/upload root cause with `--perf` evidence and bars; any proposed retry path must prove it does not increase UI-thread churn

- 2026-07-02 evidence ruled out active swap-interval constraint for the latest run: every compositor context reported `wgl_swap_disable=True` and `wgl_current_interval=0`, while Display 0 still landed around `~85-90fps` with hundreds of render `pending_skips`. That exposed a separate self-throttle: the adaptive timer treated any in-flight paint as a reason to discard the next high-refresh deadline. The fix separates queued-update dispatch coalescing from paint-delivery pending state. Duplicate dispatches are still coalesced, stale paint pending still blocks and logs `no_requeue=True`, but fresh paint pending no longer halves the intended cadence.
- the desynced transition-start seam and image-pipeline display-stagger / post-transition-prefetch resume paths no longer use private `QTimer.singleShot` ownership; missing scheduler state routes through the ThreadManager seam loudly instead of adding another Qt-timer owner.

- 2026-07-02 later evidence showed the "visualizer on Display 1 lowers Display 0 transition FPS" shape was not transition-specific or visualizer-mode-specific. The first concrete root seam was `SpotifyBarsGLOverlay.paintGL()` self-scheduling `update()` after every paint while `set_state()` already requested frames, creating child-GL overpaint (`paint≈275fps`, `update≈364fps` on a 60Hz owner). Removing paint-owned self-scheduling materially improved the old starvation pattern: follow-up logs showed no paint-delivery starvation, no cross-display topology starvation, no near-60/stable-divisor collapse, no shader/swap/fallback noise, and no severe visualizer latency.
- A tempting follow-up fix failed: capping actual overlay `update()` requests to the owning display target made the counters look cleaner but produced visible Display 1 visualizer stutter. The failure signature was `set_state≈90-100fps` while `paint/update≈39-40fps` on a 60Hz owner. This is now barred as producer-side visualizer throttling; the correct contract is one repaint request per accepted visualizer payload, no `paintGL()` self-update loop, and parser coverage for both overpaint and under-delivery.
- 2026-08-13 source reconstruction names the mechanism. The rejected gate compared a `90–100 Hz` producer timestamp against `0.92 * 1/60 s`, which accepts a `100 Hz` source only every second tick (`50 Hz`) even with immediate paint. Its pending-until-`paintGL()` latch then turned variable Qt delivery into producer admission and pushed the observed result toward `39–40 Hz`. This was not a real display scheduler: `QOpenGLWidget.paintGL()` is neither scanout nor physical-present acknowledgement. The protected Bubble trace also proves a generic phase-valid `60 Hz` latest-state sampler can completely miss its one-tick visible edge, so Phase 7 requires edge-preserving render state and source-to-visible evidence rather than a repaired rate counter alone.

Bubble worker summaries stayed stable around `1.8-2.7 ms`; transition paint durations were generally cheap; cache hits stayed `100%`; and there were no worker, shader, swap, or pending-requeue fallbacks. The concrete correction keeps playing cadence untouched but prevents confirmed non-playing state from inheriting the no-transition `100 Hz` source boost, using a timer-owned `75 Hz` paused target with low-refresh headroom. This is not the failed producer throttle: every accepted payload still requests one overlay repaint.
