### 2. On D3D11 and D3D12 the front-face rule has no negative control that bites

- **Where:** `native/core/python/host_check.py:77-82` (`NEGATIVES`); evidence `n2_2/20261113_n22_hosts` summary.
- **Evidence:** on both D3D backends `no_correction`, `rule_on_the_uncorrected_matrix` and `front_face_fixed_ccw` are
  "vacuous here (changes nothing)", because QRhi's correction leaves the x, y and w rows alone there and the rule
  chooses counter-clockwise. Only `back_triangle_culled` in the positive probe holds the rule on D3D; on Vulkan
  `front_face_fixed_ccw` is vacuous too.
- **Fix:** add `"front_face_fixed_cw": {"front_face": "cw"}` (the module already accepts `cw`,
  `native/core/src/probe_pass.cpp:81-82`): it bites wherever the rule is counter-clockwise (Vulkan, D3D11, D3D12)
  and `front_face_fixed_ccw` bites on OpenGL, so every backend has one. Then one host_check run.

### 3. The core's messenger drops two message patterns from every caller, not only Qt's

- **Where:** `native/core/src/vulkan_context.cpp:205-207` and `:218-219`; `native/core/python/vk_validation.py:85-86`.
- **What is wrong:** any message whose text contains "Mapping an image with layout", or whose id or text names
  `VUID-VkDescriptorSetAllocateInfo-descriptorPool-00307`, is counted as `qt_known_false_positive` and kept out of
  the error and warning counts, whoever called Vulkan. Qt's own debug filter hides the same two for QRhi; the core's
  own mapping or descriptor allocation would be hidden the same way. Every other excuse is bound to its Qt caller
  (A: `callers[:1] == ["Qt6Gui.dll"]`).
- **Fix:** keep the entry with its caller stack (as now) and count it as an error or warning; excuse it in
  `vk_validation.classify_group` only when the first caller is `Qt6Gui.dll`, as defect A is. The next validated
  Vulkan run shows whether anything of the core's was hidden.
