# Audit, 14 Nov 2026: N2.9 generic mode content, N2.3's leftovers and the N2.5 audit's fixes (ABI 9)

Scope: `git diff main...worktree-agent-a6db5a67c88b29537` (48 files; GitHub build at f030503e). Read-only on product
code. Opus 5.5, audit slot. No build, no load, no window on a real screen.

The branch's focused tests were run against its own worktree and its built module (read-only, no bytecode, no cache):
`test_native_visualizer_route`, `test_native_core_spectrum`, `test_native_mode_content`,
`test_visualizer_engine_packet_mailbox`, `test_native_packet_reader_sources`, `test_native_core_mode`,
`test_native_core_spectrum_program`, `test_native_core_packet_reader`: **87 passed**, none skipped. Two probes were
written for this audit and deleted afterwards. Their output is quoted below.

Counts: **0 high, 5 medium, 11 low.**

## Verdict on the parts asked about

- **Runtime schema (`mode_schema.cpp`) against the reader's invariants.** Sound. It refuses unknown keys, a schema
  id that is not `(version << 16) | 0x100 | code`, a record outside 16..65536 or not a multiple of 16, a field before
  byte 8, a misaligned, overlapping or out-of-record field, and a range rule on anything but a u32 scalar.
  `check_order` must name each ruled field exactly once, by an index in range, and the fingerprint is recomputed and
  compared. Field-name pointers are stable: Qt 6 `QByteArray` data does not move, `m_fields` is never appended to
  after `m_schema.fields` is taken, and the object is immutable behind a `QSharedPointer<const>`. The reader still
  refuses a record larger than the slot (`admit`, `found->recordBytes > m_capacity`). A schema id that is compiled in
  is refused. A mode id or code that disagrees with `kModeCodes` is refused. A code reused after unbind is harmless:
  there is no process-wide registry, each reader carries its own schema, and a retiring reader keeps its schema alive
  until the render thread releases it. Only a narrower residue remains (L6).
- **ModeSource/ModeContent lifetime and thread safety.** Sound. They follow the Spectrum item's rules exactly.
  - The program, settings and schema are taken together under `m_mutex` at one generation in `sync()` (render
    thread, GUI blocked), so the render thread never packs a record against a mismatched program or schema.
  - A rebind drops the old record, because the new reader holds nothing.
  - Readers are deleted only by `releaseRetired()` (render thread, or the last owner's destructor).
  - The node's destructor drops the content (QRhi alive), then releases the retired readers.
  - One content per item holds in one direction only (L3).
- **`program_blocks` after L2.** Every L2 item is closed:
  - non-finite and out-of-range values are refused before any byte is written;
  - a write past the block or a short stride is refused;
  - unpackable members (mat2, mat3, double, struct, multi-dimensional arrays) are always unfilled and refused by
    `set()`;
  - booleans in lists read as 0/1;
  - uints are stored as uint32.

  The tests in `test_native_core_mode.py` show this on the module. One consequence is M4.
- **Per-pass refusals.** Texture, sampler, storage, push constants, inputs, foreign blocks and a non-vec4/non-location-0
  output are all refused. One hole remains (M3).
- **H1.** The fix is correct for the product's one native backend, Vulkan on Windows.
  - In Qt 6, the scene graph's projection rect is the render target's pixel size over dpr. For a window this is Qt's
    rounded logical size.
  - The Vulkan swapchain's size is the surface's `currentExtent`, which is the native client area that
    `GetClientRect` returns.
  - So `client / window.size()` is the ratio Qt draws with. It is called on the GUI thread (from
    `VisualizerRenderItem.update()` through `route.sync`).
  - Per-axis handling in the four rotations is right: the oriented x axis takes the window's y ratio under odd
    quarters (`spectrum.py:109`), and the branch's test covers quarters 0-3 at 150 % and 175 %.
  - Parity stays bit-identical. A probe compared the card and the composite config with and without `pixel_ratio` at
    1920x1080@150 %, 2560x1440@125 % and 3840x2160@200 %: four rotations and three origins each, 36 cases, all
    identical. On the C++ side the ratio is exactly dpr there (1920/1280 = 1.5 in binary).
  - The caveats (other backends, the non-Windows fallback, cost) are L1.
- **New mode codes after the build.** No guard that protects a compiled consumer is weakened. A compiled reader
  still refuses a slot with a code it does not know (`knownMode`). A code the module has and the build lacks, or a
  renumbered code, is still a mismatch. What does not hold is the promise that a *product* mode needs no build (M5).
- **Architecture.** N2.9 matches the "one layer by default" text of Transitions.md for a *new* mode. Its shape still
  leaves the N5 ports on a second per-mode C++ layer (M5).

## Medium

### M1. The route's failure latch hides the Visualizer for the rest of the activation after a transient failure

`rendering/quick/visualizer/native_route.py:186-199` (the latch), `:206-217` (`_fail`), `:316-319` (`_placement_key`).

The latch key is `(identity, window metrics, placement)`. Nothing else re-arms it. In particular these do not:

- the settings (`spectrum.settings` at `:259-262` is inside the latched `_sync`);
- a new snapshot;
- time.

While latched, `sync` returns before `take_for_render`, so no later frame is ever tried. Probe (route on a stand-in
core at 2560x1440@150 %, `settings()` refusing once, then ten new snapshots whose settings differ):

```
first sync published: True
sync with refused settings published: False failed: True
ten later syncs with new snapshots and new settings published: [False, False, False, False, False, False, False, False, False, False]
route still failed: True settings calls after the failure: 0 snapshots left untaken: 1
```

**Failure scenario.** Any one-off failure inside `_sync` hides the native Spectrum until the mode is re-activated
or the window or card moves. In a screensaver session that is usually the whole session. Examples:

- a settings value the core now refuses (L2 refuses non-finite or out-of-range values; a zero-size card during a
  layout transition can give one);
- an `OSError` from `create_frame_mapping`;
- a refused `bind`.

A user's later Settings change that would fix the value is never seen. The hide is also abrupt
(`composite.set(visible=False)`), against "fade, never vanish".

**Suggested fix.** Latch only what cannot change without an input change (a refused bind or program, a card map that
is not whole pixels for these metrics). Retry a per-frame failure (settings, publish, take) at the next new snapshot,
and count consecutive failures so it is logged once. Alternatively, add the settings dict and the snapshot's
presentation to the key. Fade the composite out on failure. Add a test: refuse `settings()` once, then a new snapshot
with changed settings draws again. The control is the current code, which stays hidden.

### M2. `ModeContent` has no failure latch: a pipeline that cannot be built is rebuilt on every accepted frame (M2 of N2.5, again)

`native/core/src/mode_content.cpp:694-790` (`ensure`: `release()` on failure, `:784-788`), with `surfaces.cpp:258-263`.

`SpectrumContent::ensure` gained a latch keyed by (rhi, render pass, program generation) (`spectrum.cpp:839-858`).
`ModeContent::ensure` did not. Its failure path releases `m_res`, so the next `record()` creates everything again:
vertices, conventions, the clear pipeline, and per pass the buffers, bindings and pipeline. The surfaces fix clears the
dirty flag on failure, but `ModeSource::sync` marks the surface dirty on every accepted frame. A playing mode therefore
retries every frame.

**Failure scenario.** A pack without the SPIR-V or GLSL variant for the running backend, a driver that refuses a
pipeline, or M3's duplicate binding. QRhi objects are then created and destroyed about 60 times a second on the render
thread, with an error each frame and nothing drawn. This is the class the N2.5 audit's M2 closed for Spectrum. The
two copies of the stream/content code drifted inside the same branch.

**Suggested fix.** Apply Spectrum's latch to `ModeContent` (keyed by rhi, pass descriptor and program generation),
with one `noteRecorded(false, ...)` and `content_failed`/`content_failures` in the state. Add a
`generic_mode_check` case (a program whose pack lacks the backend's variant, or an item with no program) that asserts
one failure edge and `mode_resources == 0` across frames. Better still, extract the shared source/content machinery
(stream, admission, retire job, failure latch) from `SpectrumSource`/`ModeSource` so a fix lands once (see M5).

### M3. A pass without the conventions block can put a block at binding 17 and the core binds 17 twice

`native/core/src/mode_content.cpp:94-99` (`checkPass`: duplicates only among the pass's own blocks), `:764-766`
(the conventions buffer is always appended at `kConventionsBinding`).

The README asks for "any bindings but 17", but nothing enforces it. A pass that does not include the conventions
(it does not use `fragPixel`) and declares `ModeSettings` or `ModeFrame` at `binding = 17` passes `checkPass`. The
content then builds a `QRhiShaderResourceBindings` with two uniform buffers at binding 17. On Vulkan that violates
VUID-VkDescriptorSetLayoutCreateInfo-binding-00279, which is undefined behaviour: a validation error, a refused
layout, or a driver fault. Combined with M2, a refusal is retried every frame. This input comes straight from Python
bytes, the trust boundary the runtime schema is careful about.

**Suggested fix.** In `checkPass`, refuse any `ModeSettings`/`ModeFrame` at `kConventionsBinding`, whether or not the
pass declares the conventions. Or bind the conventions only when the pass declares them. Add a refusal case to
`generic_mode_check`'s blocks round with a pack that does this.

### M4. A refused frame clears the card: the mode vanishes for that frame (both contents)

`native/core/src/mode_content.cpp:805-811` and `:842-847`. `native/core/src/spectrum.cpp:953-955` and `:969-974`,
whose behaviour changed with L2 (`program_blocks.cpp` `scalarFits`).

When `packFrame` or `spectrumBlock` refuses a frame, `record()` still runs its clearing draw and skips the passes. The
surface goes transparent until the next good frame. Since L2, one non-finite f64 refuses the whole frame. Examples are
a NaN or inf in a Python simulation's field, which the reader admits because f64 fields carry no range rule, or a u32
above INT32_MAX in a field bound to an `int` member. Before L2, Spectrum wrote the NaN into one bar. Now the whole
card blinks out.

**Failure scenario.** A generic mode's simulation produces one inf (a division during a silence) and the card flashes
empty. Repeated, it flickers. This breaks "fade, never vanish" and is a regression for Spectrum.

**Suggested fix.** On a refused frame, keep the target as it is: return before `beginPass`, with no clear and no draw.
Count the refusal and report it once. Optionally, refuse non-finite values at the source: `NativeLayout.pack` refuses
or clamps them, and the reader refuses a record with a non-finite f64. Add a test that publishes a good frame, then
one with a NaN field, and checks the surface still holds the good frame. The control is the current clear.

### M5. The no-build promise holds for the harness mode only; a product mode, or a port, lands on a second layer

1. **A product mode's schema has no home.**
   - Python's transport knows only `native_schema.native_schemas()` (`_SCHEMA_MODULES`, `native_schema.py:35-37`).
     The engine worker's native publishing (`schema_for_mode`, `:230-235`) and the mailbox's decode
     (`decode_native_payload`, `:291-294`) both go through it.
   - README step 2 (`native/core/README.md:116`) says a generic mode's schema is never added there.
   - If it is added, `python_schema_table()` lists it and `schema_table_differences` reports "not in the module"
     (`rendering/native/packet_reader.py:78-84`). `NativeCore.spectrum()` and `NativeCore.mode()` then raise
     `SchemaTableMismatch`, which takes Spectrum down too until a module build.
   - If it is not added, the product's Python transport refuses the mode's frames.

   Probe Rings avoids both because its harness publishes straight into its own mapping. The route (`NATIVE_MODE_IDS`,
   `core.spectrum`) also has no generic path yet. That is fine for N2.9's scope, but D12 and the README describe a
   product mode as rebuild-free.
2. **The ports.** Every product 2D shader reads `layout(location = 0) in vec2 v_uv` and one `<Mode>Draw` block
   (`oscilloscope.frag:2,7`, `devcurve.frag:5,12`, `bubble.frag:3,10`), and Bubble samples two textures (`:78,80`).
   `checkPass` refuses all of these. So the N5 ports cannot use the generic content without rewriting the shaders
   the Python renderers also draw (README: "the Python renderer and the core draw the same file"). They would each
   grow a `SpectrumContent`-style C++ content, which is the "per-mode C++ renderer" Transitions.md's section and port
   rule (g) say never to build. Spectrum itself stays on that layer, as D12 records and defers.

**Suggested fix.**

- Split the Python registry into "schemas the module compiles" (compared by `schema_table_differences`) and
  "runtime schemas" (known to the Python transport, handed over at bind), with a test that a runtime-only schema does
  not raise `SchemaTableMismatch`.
- Widen the generic pass to the product shaders' shape: `mode.vert` emits `v_uv`; one block whose members are filled
  by name from settings plus record (BlockValues already packs by name, and the frame members are those named as
  record fields); samplers as the planned primitive.
- Alternatively, record in D12 and port rule (g) that the N5 ports rewrite their shaders to `ModeSettings`/
  `ModeFrame` and retire their Python renderer's block in the same change.
- Add a plan box for moving Spectrum onto the generic content, so that two content kinds do not stay permanent.

## Low

- **L1. H1's pixel source is right for Vulkan on Windows only, and costs a ctypes call per update**
  (`rendering/native/spectrum.py:138-168`).
  - `GetClientRect` is the framebuffer only where the swapchain takes the native extent (Vulkan). Qt's GL and D3D
    swapchains are `window.size() * dpr` rounded: 1707 x 1.5 gives 2561, not 2560. On those backends Python's ratio
    then differs from Qt's projection, and the composite misplaces silently.
  - The non-Windows fallback uses Python's round-half-to-even of `size * dpr`. It is wrong for an odd native width at
    .5 (1367 px at 150 %: 911 logical, rounded back to 1366).
  - `_native_client_pixels` runs on every update request: imports, `platformName()`, `winId()`, and a GIL-held
    `GetClientRect`.
  - The ctypes path itself is never exercised; the tests monkeypatch it.

  Fix: take the size from the render target in C++: `QQuickWindow::swapChain()->currentPixelSize()` (or the
  redirect target) in `updatePaintNode`, reported in the composite's state and used by Python. Cache the metrics and
  refresh them on the window's size or screen change. Add one test of the real path on a hidden, never-shown window
  (handle absent: the fallback).
- **L2. `sync` can still raise from its unguarded branches** (`native_route.py:179-185`): `unbind()` (`spectrum.unbind`,
  `composite.set`, `memory.close`, which raises `BufferError` with exported pointers) and `_hide()` run outside the
  `try`. Also, `_fail` logs a full traceback at ERROR for "no window yet", which is an ordinary startup state. Fix:
  guard both branches, and log the no-window case at debug.
- **L3. One content per item is enforced in one direction only** (`composite.cpp:461-467`, `:514`, `:540`).
  `bindSpectrum`/`programSpectrum` on an item that already draws a mode succeed. Both sources then sync every frame,
  and the mode silently wins (`setSources`). Fix: refuse the reverse in `bindSpectrum`/`programSpectrum`.
- **L4. Small costs on the render thread per accepted frame** (`mode_content.cpp:315-345`, `:823-825`). The settings
  buffers are re-uploaded on every draw, although they change only on a Settings change. The frame blocks build a
  `BlockValues` (a `QByteArray` and a `QList<bool>`) per pass per frame. Fix: upload settings only when
  `m_takenGeneration` changed; keep one `BlockValues` per pass and overwrite it.
- **L5. A program whose passes declare no `ModeSettings` never draws unless `{}` is sent**
  (`mode_content.cpp:474-483`, `:806-809`). `setProgram` without settings leaves `m_packedSettings` empty, and
  `record` then reports "no settings for this program". Fix: pack the empty settings when no pass declares the block.
- **L6. A runtime schema can shadow a compiled mode at another version** (`mode_schema.cpp:159-174`). The core refuses
  only the compiled schema *id*, so `spectrum` at version 2 is admitted on a generic item. That contradicts "the
  compiled table keeps the schemas a hand-written consumer reads". Fix: refuse a runtime schema whose mode code has
  any compiled schema.
- **L7. `recordFieldFits` admits lossy pairs** (`program_blocks.cpp`, `recordFieldFits`). A u32 into a `float`
  rounds above 2^24. A u32 into an `int` is refused per frame above INT32_MAX (which leads to M4). The header's
  "nothing is truncated" is not quite true. Fix: admit u32 into `int` only with an `at_most` rule at or below
  INT32_MAX, and u32 into `float` only with a rule at or below 2^24, all checked at bind.
- **L8. L9's fix is partial (harness only)** (`spectrum.cpp:515-528`, `:621-637`). `~SpectrumSource` deletes the
  retiring readers whatever `m_waiters` says. A `composite_destroy` from another Python thread during
  `composite_spectrum_wait_paused` then frees the reader and the source under the waiter, which next locks `m_mutex`
  of a deleted source. Fix: the wait holds a `shared_ptr` to the source and a reference on the reader (the
  `ReaderEntry` scheme).
- **L9. `stateJson()` reads the live reader's consumer-thread state from the GUI thread** (`mode_content.cpp:618`,
  `spectrum.cpp:766`). This is a data race on `m_refusalCause` and other members while the render thread reads.
  The pattern is pre-existing and copied into `ModeSource`; it is diagnostic and harness only. Fix: the render thread
  snapshots the reader's state into the source's report under `m_reportMutex` at each sync.
- **L10. The Spectrum latch makes a transient pipeline failure permanent for that target** (`spectrum.cpp:839-858`).
  An out-of-memory at pipeline creation stays latched until the program or target changes, and the frame driver still
  calls `setError` on every accepted frame. Fix: also re-arm on a device-lost or rhi change and on a bounded retry
  (every Nth failing record); report through the state only, not per frame.
- **L11. Test gaps.** None of these pin preset names, values or UI wording; the error-message matches are member
  names, which are structural.
  - `test_probe_rings_is_never_registered` has no negative control. A control could register a stand-in mode and see
    the test fail.
  - `generic_mode_check`'s draw round runs at dpr 1.0 only, so `fragPixel` at a fractional ratio is unproved for the
    generic content.
  - Nothing tests the route's latch re-arming (M1), `ModeContent`'s failure path (M2), the binding-17 refusal (M3) or
    a refused frame (M4).
  - The real `GetClientRect` path is untested (L1).

  The new tests otherwise have their controls: route publish/re-send, mapping unlink, bind failure, the fractional
  card map (dpr grid raises), the target guard, L1 clamp, the peek, the onedir pack check and the appended code.

## What was not verified

- Qt's own swapchain and projection arithmetic (L1, H1's premise) was not read in Qt's source for the pinned version;
  it is from Qt 6's code as I know it. Display 1 at a fractional scale (N2.8) remains the proof.
- No GPU run was made for M2, M3 or M4. They are read from the code; M1 is shown by the probe above.
