# Audit 2026-11-14: N3.8 job service, threading and lifetime

Scope: `git diff 8d63f82b^1 8d63f82b` (ABI 14), against D9 "As built (N3.8)" in `Native_Core_P3_Decisions.md`. Static
review only; no tests or GPU runs were made for this audit. Qt facts are from qtbase **6.12**
`src/gui/rhi/qrhivulkan.cpp` and `src/gui/vulkan/qvulkaninstance.cpp` (raw.githubusercontent.com/qt/qtbase/6.12),
read on 14 Nov 2026.

No high findings. Three medium, five low.

## Medium

### M1. The window's frame edge is counted once per driver, not once per frame
`native/core/src/frame_driver.cpp:277-283`, `native/core/src/surfaces.h:158`, `native/core/src/host_adapter.cpp:215,254,282`.
Every `FrameDriver` connected to a window calls `WindowSurfaces::noteEdge()` in its `beforeRendering`. A window can
have more than one driver: `WindowHost::create` reuses the window's record and makes a new host with its own driver,
and a detached driver keeps counting until it is released at its next edge (`noteEdge` runs before the `m_detach`
test).
*Failure:* when two drivers are connected (a second host on the window, or detach and attach in one GUI turn), the
counter moves 2 per frame. An entry stamped `lastUse = N` is released at Qt frame N+1 instead of N+2. Qt's
`beginFrame` of N+1 waited only for frame N-1, so the job thread can `vkDestroyImage` an image that frame N still
samples on queue 0. That is a GPU use-after-free (device fault or corruption). The product hosts each window once
(`rendering/quick/bootstrap.py:744`), so this is latent there, but harnesses and re-attach can hit it.
*Fix:* make one counter per window, not one per driver. Either `WindowSurfaces` connects its own `beforeRendering`
once, or only the first-attached "edge owner" driver counts, with ownership handed on at detach. Test it with two
drivers on one window and assert that `edges()` moves by 1 per frame.

### M2. The retire list drains only while the window renders; at rest a replaced output is held
`native/core/src/surfaces.cpp:447-476`, `native/core/src/frame_driver.cpp:280-282`, `native/core/src/mode_content.cpp:1434-1452`.
An entry is released only at a later `beforeRendering` (`lastUse + FramesInFlight`). Nothing asks for those frames:
not the commit, not `releaseFront`, not the item's removal. After an image change, the commit frame may be the last
one the window renders.
*Failure:* a window at rest after a photo change keeps the previous job output (a 4K RGBA8 photo with mips is about
44 MB of VRAM) until something else animates. This breaks D9 point 10 ("no retire entry at rest"). It also keeps
`job_images` and `job_images_retiring` non-zero, so a `RuntimeDestructionBarrier` waiting on them can time out, and
its timeout is the fail-closed exit (see M3).
*Fix:* when `retire()` adds an entry, ask for `FramesInFlight` more frames. For example, the content's notifier
queues `requestFrame()` until the list is empty, or the driver queues `window->update()` while `retiring()`. Each
request is one edge per entry, so nothing is polled.

### M3. The barrier reads process-wide counts, not the retiring generation's work
`rendering/native/loader.py:254-269`, `engine/runtime_destruction.py:532-555`.
`pending_native_work()` adds `job_images`, `mode_textures` and `mode_texture_images` for the whole process.
`job_images` includes outputs that are being shown right now as fronts (held until they are replaced), and
`mode_textures` includes every live item's textures.
*Failure:* a replacement barrier stays pending if any native-mode item outside the retiring generation holds a
texture: another display's window, a window that survives the replacement, or a successor item created before the
barrier completes. It then times out and the app exits (fail-closed). This is latent today, because no product code
drives `NativeMode` textures yet, but it fires on the first product consumer. The test
(`tests/test_runtime_destruction_native_work.py`) only feeds hand-made counts.
*Fix:* attribute the counts to items (per `CompositeItem` handle) and filter by the retiring generation's items. Or
make the barrier wait only on in-flight work (`jobs_queued`, `jobs_running`, `job_releases_pending`,
`job_images_retiring`) and leave resident textures to each item's own destruction proof. M2's fix is also needed so
that `job_images_retiring` can reach zero.

## Low

### L1. Device loss after submit is not failed closed
`native/core/src/job_service.cpp:706-719,731-735`. `QRhiVulkan::finish()` (6.12) calls `vkQueueWaitIdle(gfxQueue)`,
drops its result and returns `FrameOpSuccess`. The job ignores `finish()` anyway.
*Failure:* if the device is lost during the job's GPU wait, the job publishes an image whose upload never completed,
and Qt imports it. The service is never marked failed, so every later job tries the lost QRhi again.
*Fix:* after `finish()`, check `m_rhi->isDeviceLost()`. If that does not catch it, fence the submit yourself. On loss,
fail the job, set `m_failed`, and stop accepting jobs.

### L2. A job's non-atomic fields are read while the job thread writes them
`native/core/src/job_service.cpp:535` (`stop()`), `:573` (`stateJson`), through `UploadJob::toJson()`. `toJson` reads
`error` (a `QString`), `outputId` and the `*Ns` fields of `m_running` while the job thread may be inside `fail()`
(`error = why`) or writing the times.
*Failure:* a data race. Copying a `QString` while another thread assigns it can touch freed shared data (crash or heap
corruption). The window is narrow: `stop()` during a failing job, or a harness polling the state.
*Fix:* for `m_running`, report only `name`, `generation` and `state()`. Or snapshot the fields under a job mutex that
`fail()` and the writers also take.

### L3. A thread that fails to start leaves jobs queued forever
`native/core/src/job_service.cpp:279-284`. `QThread::start()` returns nothing; on failure Qt prints a warning and
`isRunning()` is false.
*Failure:* every job stays queued and never fails. An item's first picture is never drawn (no in-frame fallback), and
`jobs_queued` holds the barrier.
*Fix:* after `start()`, if `!m_thread->isRunning() && !m_thread->isFinished()`, set `m_failed` and `m_quit`, return
`false` from `submit` (the consumer falls back to in-frame), and fail the queued jobs.

### L4. The lost-texture listener outlives its owner's retire
`native/core/src/item_notifier.cpp:17-35`, `native/core/src/module.cpp` `PyTexturesLostListener`,
`rendering/native/mode.py:192,227`. The core holds a strong reference to the callable until `~CompositeItem`.
`NativeMode.retire()` does not clear it.
*Failure:* between the owner's retire and the item's deletion, a lost edge calls into a retired owner, and a bound
method keeps the owner alive. Delivery itself is safe: it is gated on `m_item`, queued with the item as context, and
released on the GUI thread.
*Fix:* clear the listener in `composite_mode_retire` (GUI thread), or have `mode.py` hold a `weakref.WeakMethod`.

### L5. The textures do not switch together when an import fails
`native/core/src/mode_content.cpp:1673-1701` with `importOutput` at `:1577-1606`. The commit swaps texture by texture.
If `createFrom` fails for one texture, the others still switch and the failed one keeps its old front, or none. An
abandoned job is also reported as "could not be uploaded: " with an empty reason.
*Failure:* a transition can pair a new picture with an old one, which D9 point 3 rules out. This needs an import
failure, which is rare.
*Fix:* commit in two phases. `createFrom` every done output into temporaries first, then swap all of them only if
every import succeeded. Otherwise release the outputs and report the item's changed textures as lost together. Give
an abandoned job its own reason.

## Checked and sound (no finding)

- **Latch.** `publish()` is a CAS with ordered semantics, made after the output fields are written. The consumer
  reads `state()` with acquire, then the fields. `cancel()` against `start()`, `publish()`, `fail()` and `abandon()`:
  every case ends in exactly one terminal state, and an output is dropped exactly once: by the job thread if
  cancelled while running, by the consumer's `release` if it was published first, by the teardown if abandoned. The
  frame request comes after `publish` (`fetchAndAddOrdered` on `m_jobsFinished`), so a sync that sees the count also
  sees `Done`, and no wake-up is lost.
- **Lock order.** No cycles. `registryMutex` is released before `JobService::m_mutex`. The `WindowSurfaces` mutex is
  released before `service->release()`. The `ItemNotifier` mutex only posts an event. `UploadJob::m_pixelsMutex` is a
  leaf. The job thread never waits on the GUI or render thread, so `stop()`'s join on the GUI thread cannot deadlock.
- **Textures switch together (normal path).** Nothing commits while any candidate is pending. All candidates commit
  in one record, before `ensure()` rebinds, so no draw uses a released wrapper. A frame never waits for a job.
- **Retire stamp.** Assuming one counter per frame (see M1), `lastUse` is the edge of the record, or the edge before
  a sync-time node deletion, so it is at or after the last frame that sampled the image. Release comes at
  `lastUse + FramesInFlight`, after Qt's `beginFrame` waited on that frame's slot fence. The hidden host's offscreen
  frames are stricter (each `beginOffscreenFrame` waits for the previous one). A `finish()` followed by
  `releaseAllRetired()` at invalidation is sound.
- **Vulkan: two QRhis on one device.**
  - *Queue access.* Qt's QRhi only waits on its own queue. Its 6.12 source has no `vkDeviceWaitIdle`: `destroy()`,
    `recreateSwapChain()`, `releaseSwapChainResources()` and `finish()` each call `vkQueueWaitIdle(gfxQueue)`. So
    queue 1 is only ever touched by the job thread, and the job QRhi's `destroy()` only touches queue 1. The external
    synchronisation rule on `VkQueue` holds. The module's own `vkDeviceWaitIdle` comes after the join and after Qt's
    QRhi is gone (`vulkan_context.cpp`, `destroy()`).
  - *Shared Qt state.* `QVulkanInstance::deviceFunctions` locks `deviceFuncsMutex`. Each QRhi has its own VMA
    allocator (`vmemAllocator = nullptr`), pools and pipeline cache.
- **Vulkan: import, ownership, layout and sync.**
  - *Ownership.* Same family, exclusive images. QRhi uses `VK_QUEUE_FAMILY_IGNORED` in every barrier, and no
    ownership transfer is needed within one family (facts C3).
  - *Layout.* After `uploadTexture`, `usageState.layout` is `TRANSFER_DST_OPTIMAL`. The GenMips branch puts every
    level back to `origLayout` (also `TRANSFER_DST_OPTIMAL`) and does not change `usageState`. So
    `nativeTexture().layout` is one layout for all levels, which is what `createFrom` needs.
  - *How Qt's QRhi picks it up.* `QVkTexture::createFrom` sets `layout = src.layout`, `access = 0`, `stage = 0` and
    `owns = false`. Its first transition uses `srcStage = TOP_OF_PIPE`, and `destroy()` defers only the image view
    (`image` and `allocation` are nulled).
  - *Sync.* There is no semaphore. The fence signal of `vkQueueWaitIdle` on queue 1 makes the job's writes
    available. The host wait, then the atomic release/acquire, then Qt's `vkQueueSubmit` on queue 0 form the
    execution chain. Qt's barrier (dst `SHADER_READ`, with the layout transition) makes the writes visible. This is
    a valid dependency, not undefined behaviour. Qt documents `createFrom` of a native `VkImage` as the import route;
    "not shareable" refers to `QRhiResource` objects. Destroying the `VkImage` before Qt's deferred
    `vkDestroyImageView` is allowed once no submitted work uses either.
- **Teardown.** `VulkanDevice::destroy` runs in the window's `destroyed` handler, after `~QQuickWindow` released Qt's
  QRhi, and in the hidden host after the render control. It stops the service first: in-flight work is abandoned
  after its GPU wait, queued jobs are abandoned, the backend is torn down on the job thread, then the thread is
  joined; only then come `vkDeviceWaitIdle` and `vkDestroyDevice`. A late shared owner of the service (a content's
  `m_service`, a retire entry) only meets an idempotent `stop()`.
- **Notifier.** `~CompositeItem` detaches first, under the notifier's mutex. Posts use the item as context, so Qt
  drops them if the item is deleted. The listener is set, called and released on the GUI thread only, so the job
  thread never holds the last listener reference.
- **Rest.** The job thread parks on `QWaitCondition` with no timeout, starts at the first job, and never takes the
  GIL. The frame edge costs one atomic read-modify-write (`noteEdge`, not "one atomic read" as D9 point 10 says) plus
  one atomic read.
