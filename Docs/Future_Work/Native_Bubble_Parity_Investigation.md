## Ownership and eliminated explanations

`rendering/quick/visualizer/implementations/bubble.py` builds the shared frame and draws ambient points and hero mask before the final Bubble pass. `rendering/quick/visualizer/native_route.py` declares the same point/mask shader files, target formats (RGBA8 coverage and RGBA16F light), streams and final shader. `bubble_native_schema.project` consumes the same frame values and ambient payload. Source review found no separate simulation or authored-data owner.

- The mask's custom erase blend is wired: `parsePassTargetState` preserves the custom output state, `outputBlend` selects it, and geometry pipeline construction supplies it to `setTargetBlends`. A serialized preset label of `replace` is not evidence that the custom erase was omitted. Source inspection does not substitute for inspecting the actual built pipeline and attachments.
- Both paths in the current rule-(a) comparison draw instanced quads. The earlier `.artifacts/evidence/native_core/n5_1_bubble/20261115_quads_vs_points/figures.json` compares Python points with quads; it cannot explain or authorize the present native-versus-Python quad residual. Its old light-error script uses an absolute 1/255 threshold despite an FP16-step comment; those figures do not prove ULP parity.
- Python's ambient allocation is exact while native targets may round allocation to 64-pixel buckets. `widgets/spotify_visualizer/shaders/bubble.frag` maps through actual texture size, clamps to content texel centers and accounts for row convention. This is a real path difference worth isolating, not an established cause. RGBA16F on both paths alone establishes neither equal sums nor unequal sums.
- The retained run used DPR 1.5, not DPR 1. Neither a point-coordinate difference nor a presumed shader compiler/orientation defect is established by the current images.

## Reflected CPU packing and live upload

`.artifacts/evidence/native_core/n5_1_bubble/20261116_block_oracle/` retains the canonical input-244 block oracle, independent Python packing, reflected layout, negative control and raw bytes. The GPU-free `mode_blocks` comparison passes all 3,552 compared shader-read bytes: 49 positions/extras, 147 trail.xyz samples, two addressable class words, enabled ambient size and scalar/style fields; reflected offsets and ambient non-core settings agree. A serialized position mutation is caught. This proves CPU packing for those checked spans, **not GPU upload**. It excludes inactive array tails, intentional conventions and target-size fields: `mode_blocks` supplies no per-pass target sizes, while a live draw does (the helper supplies overall 630×420 rather than the actual ambient 618×408). That helper limitation is not a live target-size defect. It also does not prove shader evaluation, attachment rendering, blending or pixel parity.

A later synthetic debug draw isolates 841 active scalar values into an R32F target, with class words split into exactly representable 16-bit halves. It uses the canonical BubbleDraw declaration and captured record; baseline, real serialized position and class-word mutations, and restoration are retained in `upload_opengl.json` / `upload_opengl.npz` and `upload_vulkan.json` / `upload_vulkan.npz`. On OpenGL, columns 835 and 836 read **0 and 0** instead of **34114 and 1** for baseline class word 1 (99650). Toggling that word's bit 16 changes the expected word to 34114, but the OpenGL class-word negative control does not change the corresponding output. Position mutation and restore controls work, all rows agree, and records/readbacks/retirement checks pass. The Vulkan run matches all 841 values for baseline, both mutations and restore, including the class-word negative control; validation has no unexplained findings. This debug draw is strong evidence of an OpenGL upload defect, not by itself proof that it explains every Bubble pixel difference.

The independent CPU investigation (`upload_cpu_investigation.json`, `UPLOAD_INVESTIGATION.md` and retained `qrhigles2.cpp`) confirms the reflected `uint[4]` member at offset 192 with std140 stride 16. Native CPU bytes contain baseline `[1627389967, 99650, 0, 0]` and mutated `[1627389967, 34114, 0, 0]` exactly. In pinned [Qt 6.12.0's OpenGL QRhi source](https://github.com/qt/qtbase/blob/v6.12.0/src/gui/rhi/qrhigles2.cpp), the signed-int array branch depads and uploads its array, whereas the unsigned-int branch at lines 4815–4817 uses `glUniform1ui` once and ignores the array dimension. This predicts word zero being uploaded while later unsigned scalar-array elements remain zero; it explains the observed debug-draw behavior without blaming the CPU packer or its address arithmetic.

The Vulkan debug run reports five attributed Qt-A findings and zero unexplained validation errors or warnings; its registry-loader warning is recorded separately. All checked resources and hosts retire. The OpenGL run inherited `QSG_RENDER_LOOP=threaded`; it is recorded as an existing harness environment condition, not a newly added configuration or a clean-environment timing claim. These are correctness probes, not benchmarks.

The repair is planned/in progress, not yet proved fixed. One canonical `uvec4` preserves the same four-u32 record and avoids the broken array upload, with exact record-sequence-to-vector admission at the shared owner. Refuse multi-element unsigned/bool uniform arrays under the current portable contract; declared length-one arrays remain supported and storage buffers are outside that restriction. The compatible representation and admission need focused negative controls, a matching official module, both-backend live upload checks and the original owner parity gates. Preserve exact 32-bit words and fail-closed type/count/range handling; do not route them through float or silently add a backend fallback.

The source review's `reproduce_owner.py` and the executed copy beside the current baseline preserve the process-local dormant-registration method; they do not register Bubble in product settings. The plan's widened offers and placements, rule-(b), block/item negative controls, performance, rest and retirement proofs remain required before registration.
