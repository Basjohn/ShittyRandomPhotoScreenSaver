# Live Settings without global display teardown | cross-profile implementation plan

**Status:** OPERATOR-APPROVED PLANNED WORK, **NOT IMPLEMENTED** (23 November 2026).
**Live admission:** `Current_Plan.md`, item 1B.8 **after M4 Unified Appearance Theme and Theme Studio**, within the post-Concrete-Rain product QoL phase; does **not** block N5.8 native Studio migration, NF Vulkan flip, Melt Pool, Concrete Rain, or already admitted material/theme work. All profiles are in scope: Standard screensaver RUN/CONFIG, Dashboard, diagnostic, and **future SMP when it is separately admitted**. No SMP implementation is authorised by this item.
**Source precedence:** this *later planned policy* supersedes the future-facing "Settings must always destroy the display" assumption only **once all gates here are accepted**. Until then, `Spec.md`, `Docs/Contracts.md` and the existing `engine/engine_handlers.py` destructive Settings path remain the implemented and tested current contract. Historical incident reports are not to be edited or reinterpreted as evidence that a new design has already shipped.

## 1. Outcome, priority and non-negotiables

Opening, browsing, editing and closing the EXISTING QWidget Settings dialog should not destroy a healthy running display generation. A settings change should touch **only its necessary owner(s)**, while all unrelated displays, providers, Qt Quick scene graphs, native GPU resources, UI and, where present, audio playback remain alive. The exact same architecture serves Standard, Dashboard, diagnostic and future SMP, with profile-specific admission, focus/input/security and dormancy policy. Do not fork an independent settings engine or screen-saver runtime for SMP; do not rewrite the complete Settings dialog in QML to get the lifecycle change.

**Disruption hierarchy, in binding order:**

1. **No presentation interruption:** browse/close unchanged, or live apply reversible semantics in the existing owner with no recreation and no fade.
2. **Precise capability-local transaction:** quiesce, retire or replace only affected service(s), widget subtree, Visualizer simulation/render content, render targets, display binding or provider lease. Unrelated owners survive. Any affected content retains its normal stable presentation where legal; no extra fade just to conceal implementation flaws.
3. **Second-last resort: coordinated fade OUT, stage the substantial but valid reconfiguration, then fade IN.** Use this when an otherwise safe change cannot produce a smooth continuous image, or has a first-authoritative-frame discontinuity. Fade the narrowest affected screen/region, use the existing compositor animation/clock and generation-scoped reveal guards, and do not stop playback or other unaffected displays.
4. **Absolute LAST resort: full generation teardown and replacement**, only when a proved hardware/device/backend/topology/ownership incompatibility, failed local recovery or explicit structural change truly prevents safe retention. Invoke the existing strict engine-owned, non-reentrant destruction barrier and recreate from committed state. Do not use teardown as a blanket safety blanket, a shortcut for missing per-feature cleanup, or the default result of visiting Settings. A failed destruction barrier remains fail-closed/fatal under the current contract; no "hide-and-hope" fallback.

**The ordering is a policy, not an assertion that any particular setting is already hot-applicable.** Every key / capability is audited and assigned a decision class by its **real owner**, not classified by its Settings page or UI control. Uncertainty means defer / reject / require restart, not an opportunistic unsafe live write. Nothing silently promotes a destructive setting to live because a GUI was rewritten.

**Ownership and resource management must measurably IMPROVE or at minimum never regress.** One GUI/event-loop authority, canonical SettingsManager/store, one active application-service registry, one logical Visualizer and capture/analysis owner, one display-generation admission controller, lawful Qt/QRhi GPU-thread owners, and deterministic subscription/resource lifetime. No new global hidden singleton, second compositor, duplicate QML engine per open, scenegraph clone, audio lane, polling owner, periodic retry timer or shadow "temporary runtime" may be left resident. Dormancy is an independent acceptance requirement, not a trade-off for convenience.

## 3. Architecture: one explicit SettingsSession and owner-classified change plan

**Keep the existing SettingsManager as SSOT.** Add one engine-owned `SettingsSessionController` (name illustrative, no second settings database) holding the *session identity*, application/profile and permitted desktop, Settings dialog generation, original committed settings revision, working preview/transaction record, changed-key set, lifecycle state, and cancellation/admission tokens. It is not owned by the display generation; it never caches a Qt GPU pointer or a service instance across generation retirement. Its only strong window references exist during its bounded session and are cleared after closure; late signals are fenced by both session identity and the relevant affected-owner identity.

**State machine:** `CLOSED -> OPENING -> OPEN -> APPLY_PREPARING -> APPLY_COMMITTING -> OPEN`, with `CANCELLING / CLOSING / CLOSED`, a separate `FAILED` that triggers an explicitly classified recovery. Exactly one Settings session per application; a repeated request focuses the existing session if its desktop/profile policy permits, otherwise is ignored with a log. A stale queued action can neither commit nor re-open after session close. Idle closed state has no extra threads, timers, subscribers or render resources.

**Studio is an explicit sub-state of the SAME Settings session, not a second session:** `OPEN -> STUDIO_STARTING -> STUDIO_ACTIVE -> STUDIO_RETURNING -> OPEN`. This is a **window visibility handoff**: Settings is visible until Studio's first presented frame, then **Settings is concealed for the entire Studio session**, and restored as the same Settings QWidget afterward. Live Settings does not mean Settings stays visible beside Studio. See `4 and automated gates A2/A3.

**Seams:**
- **UI** retains current lazily constructed tabs and Settings style. Its events submit typed read/edit/preview/apply/cancel intents to the controller; it cannot claim a GPU/device change is safe. Use a supported non-modal Qt open/visible lifecycle with normal top-level widget paint; do not install another `QEventLoop`/`QDialog.exec()`-style nested loop as the new Settings owner. Preserve CONFIG/startup route deliberately until its separate acceptance passes.
- **Planner/classifier** maps exact canonical keys and capability metadata to owners, dependencies, side effects and one of `LIVE_REVERSIBLE`, `LOCAL_REBUILD`, `FADE_TRANSACTION`, `GENERATION_REBUILD`, `RESTART_REQUIRED`, `EXTERNAL_SIDE_EFFECT`, or `INVALID`. The safe action is a decision of the backend owner and its measured capability, **never** UI location alone. Unknown keys are rejected/deferred, not treated as LIVE.
- **Owner adapters** are bounded services on existing per-feature boundaries (appearance, ordinary card, media, provider sources, animation, Visualizer, scene geometry, display/topology and process-scoped service). Reuse canonical descriptor and setting declarations. No per-tab reimplementation of resource management.
- **Transaction** validates the complete affected dependency closure, obtains a revision/generation guard, stages the new state and fresh resources without publishing incompatible half-updates, fences and releases only affected old leases/owners, atomically publishes the new canonical projection, then releases its admitted old resources. Concurrent edits coalesce to the latest intent; unrelated provider updates still run. **No cloning of the full Qt scene** for preview.
- **Commit/Cancel:** existing `SettingsUndo` remains 30 in-dialog user gestures; it is *not* a transactional restore point. A separate narrowly scoped durable preview/Apply/Cancel record restores only reversible state if cancelled, without rolling back unrelated SettingsManager changes. Account/network actions, file deletion, cache clear, folder scan, device reinitialisation and credential changes are explicit side effects with confirmation, cancellation or "applies immediately" semantics; never falsely promise rollback. Settings close/save must be idempotent, atomic where the existing store supports it, and unaffected hidden tabs must not mutate state.

**Per-setting impact plan (initial admission targets, subject to real preflight):**

| Class | Representative setting | Expected action / rollback |
|---|---|---|
| NO_CHANGE | open, browse, close, switch Settings tab | Do nothing to displays, frames, services or data; no fake publisher signals |
| LIVE_REVERSIBLE | semantic theme, typography, colours, opacity, material/border, safe Visualizer Studio parameters, HUD presentation | Project once on existing owners, maintain fresh per-surface contrast/material; rollback only affected projection |
| LOCAL_REBUILD | enable/disable one widget family, provider source or Visualizer mode; reconfigure capture/audio analysis or card render content | Quiesce affected owner; release only its resources/subscriptions; re-admit same host if legal, validate first authoritative frame |
| FADE_TRANSACTION | major visual/layout/geometry change with real discontinuity even though owners can stay valid | Stage change, fade affected content out, commit at invisible boundary, validate, fade in; unrelated displays/Media needn't fade |
| GENERATION_REBUILD | irreconcilable QRhi window/graphics device/topology, unrecoverable render-owner invalidity, backend change where restart not mandatory | Engine owns full barrier, later-turn admission, full release before replacement, exact identity and safe rebuild; not a default |
| RESTART_REQUIRED | process-global Qt application/graphics backend change or packaging-level change not safely re-creatable | Persist request with clear restart notice; do not attempt a half-migrated device |
| EXTERNAL_SIDE_EFFECT | deleting caches, network account operations, library edits, credential/browser handoff | Explicit confirmation/durable semantics; cannot pretend Save/Cancel undoes external effects |

The exact final matrix MUST be derived by scanning all existing settings keys and each live consumer at implementation time, including unusual Custom layout, per-mode technical profiles, fullscreen, widget family disable, display routing, sources and data-pool membership, theme/profile migration and archive/onboarding commands. No generic "all keys under widgets are live" fallthrough. Classify setting dependencies and *ability to undo* separately. Prove the affected-subgraph minimum using negative controls that detect unnecessary re-instantiation of other owners.

## 4. Dormancy, Visualizer, Media and source rules

- **A temporarily suspended feature is NOT retired.** Retained paused state is deliberate and bounded; no logical tick, GPU render, capture/DSP lease, new preview simulator or periodic hidden work may survive when the relevant dormancy owner says parked. Existing mode/preset/camera/authored geometry stays stable. Resume re-acquires leases, rebases clocks and disallows old audio/geometry/render publications until a current admitted frame is ready. Parking reasons compose (Settings, display power, covered fullscreen, visibility, user pause): clearing Settings cannot silently unpark a display still off or covered.
- **A disabled capability IS retired**: zero heavy constructors/imports before admission, release effect-specific GPU objects on proper context, unsubscribe provider/SMTC/COM/lazy jobs, cancel timers by owner identity, and leave no retained child/bridge or glib timers. Re-enabling acquires exactly one owner and restores canonical settings, not leaked hidden objects. A family that becomes unavailable must not leave a silently ticking orphan.
- **Media/SMTC/playback:** Dashboard Media survives ordinary Settings access wherever source/network policies permit. Future SMP decoder, WASAPI device and queue are process-scoped and NEVER inherit presentation generation lifetime; change the exact output device only in its explicit service transaction, not every Settings open. Keep one logical Visualizer and one beat engine; SMP continues to require the Visualizer parked while Settings is open and media/audio visible and playing. For Standard/Dashboard define equivalent power/visibility/interaction policy explicitly and prove idle cost, without changing the screensaver's exit-on-input semantics.
**Both Visualizer Studio and Theme Studio MUST conceal Settings rather than coexist visibly with it. Binding lifecycle:**

1. **Launch/handoff:** keep one live Settings session and its exact same QWidget. Construct the Studio using its approved top-level Qt Quick host. Keep Settings on screen and working until the Studio confirms its **first authoritative presented frame**, then conceal Settings, preserving its QWidget and session. No overlapping two-editor user experience; no Settings taskbar minimization, replacement window or full runtime teardown. The approved native `ui/studio/presence.py` conceal path may be adapted to non-modal Settings, but must preserve its visible result, not blindly change `exec()` to `show()` or `hide()`.
2. **Active Studio:** Settings is **fully concealed, non-interactive, not keyboard focusable and not drawing behind Studio**; no Settings popup, tooltip, focus, Alt+Tab/minimize or input capture interferes with Studio. Its tab, nested page/pill, scroll, selected visualizer/preset, Custom state, undo and active session remain retained. One Studio/editor input owner, one Settings session, and no duplicate live Visualizer/beat engine. The authorized Studio preview renderer may run on its own recorded/synthetic inputs as before; hiding Settings must not inadvertently resume a parked production Visualizer or introduce a second capture source.
3. **Studio-to-Studio/mode switch:** Settings stays concealed between consecutive Studio hosts; do not flash/activate it during a mode switch. The prior Studio retires before a successor gains input; do not proliferate QQuickWindow/QQmlEngine owners.
4. **Close/return:** normal Close, Esc, X/Alt+F4, Save, Cancel, first-present failure, surface loss, exception or cancellation must either restore the *same* Settings QWidget or, if the entire application is legitimately exiting, retire the entire session cleanly. Preserve the existing **one-transition** exit: reveal Settings underneath the still-covering Studio **without activating it**, perform needed HWND expose/Qt repaint (layered-window `WM_PAINT` trap), then foreground/activate Settings **only after the Studio window has disappeared**. Prevent the documented double-focus swap, missing paint/frozen window and late use of deleted Shiboken wrappers. Idempotent finally/cleanup must not resurrect a destroyed Settings window. Studio first-frame failure leaves Settings visible and displays an appropriate error.
5. **Conceal, not ordinary OS minimization:** minimizing can introduce taskbar/Alt+Tab icons, extra activation and window-state surprises. Prefer proven native conceal. Platform-specific implementations can differ only with equivalent hidden/restore and focus behaviour.
6. **R-49 is NOT a precedent for forbidding UI concealment:** hiding a valid Settings window while Studio is active is not hiding a partially retired GPU display runtime. Live, parked and retired owners are explicitly distinguished, separately accounted and fenced. Do not recreate hide-only half-stop or confuse Settings visibility with GPU resource ownership.
- **Configuration/Save policy:** don't rewrite runtime defaults, curated visualizer presets or user-authored theme/layout files just because Settings is open. No actual preset may be used as a test input or golden, including a Settings round-trip. Synthetic temporary fixtures test the roundtrip; real authored files remain freely editable. Respect existing source refresh and one source of Settings/capability truth.
- **Multiple displays/DPR:** unchanged display generation identity remains stable across no-change Settings; a scoped display reconfigure cannot mutate another display's renderer or compositor. Test 100/125/150/200% DPI, moved Settings window, monitor disconnect/reconnect, DirectX/Vulkan/GL fallback if applicable, fullscreen overlays, transitions, mixed-refresh monitors, and no extra work on an unused GPU.
- **No extra UI rewrite requirement:** QWidget Settings already uses software QPainter + native Windows material composition. Do not introduce `QQuickWidget`, another raster/video capture layer, new QQmlEngine just for Settings or SMP-only Settings renderer. Only consider replacing presentation technology on separately measured visual/product grounds.

## 5. Secure desktop / Winlogon / screensaver admission (HARD SAFETY GATE)

The screensaver may run in a Winlogon/secure or other restricted desktop context.
The new live Settings architecture must **preserve the current saver input, Settings
request and secure-desktop behaviour exactly**; it must never hijack, block, delay
or visibly disturb Windows login/lock/credential presentation. **Do not
invent a new restriction saying all secure-desktop Settings requests are
forbidden:** first inspect the real old `/s`, `/c`, preview and keyboard
routes, because a previously supported, explicitly admitted Settings
interaction must not be silently removed. Equally, a healthy retained
renderer is **not** permission to create any *additional* interactive
Settings/Studio HWND or perform an action that the original secure route
did not permit. If the old route uses stop/exit and an interactive-user
handoff, retain it there until a safe replacement is independently proven.

- Distinguish Standard `/s` saver, `/c` configuration, `/p` preview, Dashboard, diagnostic and
  future SMP **AND** the actual desktop separately. `core/windows/desktop_context.py::
  is_interactive_user_desktop` answers whether **account/browser/credential-only**
  operations are permitted on interactive Default; Winlogon and unknown remain
  denied for those operations. **Do not misuse this account permission predicate
  as an invented blanket denial of the existing Settings request.** Audit the
  current allowed saver Settings route and retain precisely its pre-existing
  admission/exit behavior under real secure desktop conditions. New live
  dialog behavior on such a desktop requires *additional* real validation,
  and if it cannot be proved, follow the old safe route. No env/process-name
  inference, extra top-level HWND, shield, mouse grab, modal event pump or
  foreground/taskbar promotion that could disturb Winlogon.
- Preserve canonical saver input/exit rules, secure URL handoff, Gmail/Steam account/browsers, credentials, system lock/unlock and session changes. Do not run a browser, OAuth, shell open, helper child or credential flow on Winlogon. Account-only UI remains restricted to proven interactive Default desktop, consistent with `Docs/Contracts.md`; opaque/unknown context fails closed. Do not trust `SESSIONNAME`, presence of Explorer or elapsed time as evidence of safe foreground access.
- **No Windows display flicker regression:** the historical A-01 "security-style placeholder" was caused by HWND teardown on the destination monitor, not by a Winlogon popup. Never conflate the two. Measure Dashboard window identity and Settings-window focus/placement before/after. No extra shields or blackout windows on untouched monitors.
- Acceptance matrix: secured saver active/on lock screen and unlock, preview and `/c` config, interactive saver test, interactive Dashboard, multiple desktop sessions, monitor/DPR/refresh changes, RDP/remote session where supported, denied/unknown desktop, app stop while Settings-opening callback is queued. Prefer **automated real-Windows GUI/HWND/Qt focus and desktop checks** wherever safe, with fake restricted-desktop negative controls. Those tests reject **newly unauthorized** Settings UI/actions, without removing existing saver Settings interaction. Tests cannot circumvent a real lock screen. Changing the secure route needs separately proved actual Windows behaviour; retain the existing secure route when this cannot safely be automated, without delaying verified interactive profiles.
- **Security wins over convenience:** if secure-desktop lifetime cannot be demonstrated, leave the existing safe `.scr` route unchanged until validated; Dashboard/interactive modes may still acquire the shared live policy. A global "all profiles" checkbox is NOT proof that a secure route can accept it.

**What still needs human judgment?** Only an aesthetic choice that cannot be scored responsibly, or a protected-desktop interaction requiring controlled real Windows access and not safely automatable. Do not turn those into a blocker for unrelated green profiles. Report unproven secure paths as **unchanged legacy**, not falsely green. Automated real Qt/Win32 window visibility, opacity, focus, z-order, event sequencing, expose/repaint and memory measurements replace routine operator screenshot reviews. Honor existing project-level permission for agents to initiate heavy game-load runs; this does **not** apply to ordinary non-load automated proofs. No agent should claim A2/A3 green solely by reading QML source or checking a mock.

## 7. Negative controls and failure criteria

- Fake a stale old display manager/generation during async Apply: **must reject**, preserve existing committed state and perform no stale UI publication.
- Submit an enable/disable while a provider frame, a transition and a late source callback are in flight: disable must release only its capability, and late callbacks must fail closed.
- Inject GL/QRhi release error, lost context/device or owner reentrancy: **never** pretend the resource was freed or clear a raw handle; full barrier or explicit abort after safe owner fencing; never allow second renderer/engine.
- Repeated close/open, Studio surface failure, nonmodal Settings focus loss, Settings disappearance, invalid Shiboken wrapper, layered HWND hidden->shown: no crash, no nested-loop ghost, no app-modal focus ping-pong, no repaint deadlock, no permanently invisible settings. The **A2/A3 automated negative controls** also reject a visible/interactable Settings while Studio is active, premature concealment before first frame, minimizing instead of concealing, a Settings flash between Studios, and returning to a different Settings QWidget.
- Change a backend- or process-global Qt attribute while running: defer/restart and state why; no partial swap to an incompatible API.
- Park on Settings, also park for display power, then close Settings: still parked until display power resumes. A stale pre-park audio packet cannot become first visible frame; no dt jump.
- Enqueue a valid Settings action, then switch to Winlogon/unknown before
  dispatch: revalidate the **actual permitted original route**; never
  open an extra unauthorized GUI or silently change the original secure
  Settings input/exit behavior. Fail any cross-desktop ShellExecute,
  browser/OAuth or unauthorized new foreground window.
- Force malformed/unsupported setting or an irreversible side effect then Cancel: refuse unsafe apply, and do not claim rollback of network/disk changes.
- Collect and compare **synthetic, test-owned** settings snapshots and configuration manifests; no actual authored visualizer preset is an automated test input, pinned key, filename expectation, pixel/screenshot golden, or forced reset.
- Verify no-change GUI display identity survives 50+ opens; targeted Visualizer family retirement changes exactly its related identity, all siblings remain; fallback destroys old owners once, seals barrier, then constructs replacements once. Check both real GPU backends in the supported matrix.
- If Winlogon tests cannot be completed, promote only proven interactive
  policies and keep the existing secure saver Settings route/exit contract
  unchanged. Never silently weaken account/desktop gates to score green,
  and never disable a previously supported saver Settings action by
  assuming it was a security problem without evidence.

## 8. Scope exclusions and unmodified commitments

- No Settings UI rewrite to Qt Quick, no SMP library/player, no change to theme-scope or skin authority, no alternate process-wide "background instance", no now-playing interruption, no synthetic GPU test pretending to prove real Winlogon behavior.
- No relaxing **existing** full-stop destruction and device-loss guards while new local retirement is unproven; no suppression of errors and no zombie QObject/GL state to keep an animation smooth.
- No return to hide-only R-49; **running**, **parked** and **retired** must each be explicit, accurately accounted, and cannot be conflated.
- Do not delay native parity, native Studio N5.8, NF, first new Vulkan modes, M4 or Theme Studio. Do not change the operator's deferred-SMP decision, and do not silently satisfy SMP's later M8 audio/library-specific live-setting obligations.
- Keep Windows secure desktop requirements first-class and provide existing Linux GUI adaptation or explicit inert/no-op behavior for Windows-specific HWND/desktop features. Do not add environment-variable configuration.
- If a particular owner cannot yet support a safe local update, **classify it** and use an existing accepted defer/restart/last-resort destruction path with an explicit reason. A temporary limitation is preferable to a leaked or poisoned runtime.
