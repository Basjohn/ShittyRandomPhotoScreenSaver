## 2026-07-15 Whole-Process Resource Profiling Audit

This is a profiling and attribution backlog, not permission to lower refresh rates, visual quality, transition fidelity, widget content, or live visualizer response. The opt-in `--usage` sidecar now supplies low-cadence main-plus-child CPU, system CPU, memory, thread/handle/IO, ThreadManager activity, Windows per-process GPU engine, VRAM, sampler-cost, and cadence evidence without tray polling or UI-thread collection. The remaining items deepen attribution beyond that baseline. Any new instrumentation must remain dormant outside an explicit diagnostic flag, sampled off the UI thread where OS APIs are involved, and emit bounded summaries rather than per-frame log traffic.

- [ ] **P0, very high reward: make compositor timing telemetry truthful across every transition family.** Of 26 transition summaries, 25 reported `paint_fps=0` and all 26 reported zero GPU samples; current production call search shows `TransitionProfiler.tick_paint()` and `tick_gpu()` wired only through the Slide renderer. Meanwhile the same summaries contain CPU/timeline `dt_max` values up to `171.10 ms`, so the logs cannot distinguish render-timer delay, paint/event-loop starvation, swap blocking, or GPU saturation for Warp, Particle, Blockflip, Raindrops, Wipe, Diffuse, Burn, and other active families. Route paint timing through the shared compositor paint seam and use non-blocking GL timer queries with delayed result collection where supported. Never use `glFinish()` in ordinary profiling because it changes the workload being measured. Log sample counts/support state so zero means measured zero only when samples exist. **Reward:** converts the highest-value runtime-health logs from ambiguous to actionable and prevents cadence fixes being aimed at the wrong owner. **Acceptance:** representative 165/60 Hz dual-display runs produce render, paint, and GPU sample counts for every exercised transition, preserve identical pixels/durations, add no repaint/update calls, and keep instrumentation-off overhead statistically indistinguishable.
- [ ] **P1, high reward: run controlled leak slopes rather than comparing isolated snapshots.** Profile at least 60 minutes with repeated image transitions, visualizer hotswaps, Settings stop/restart cycles, Steam/Reddit refreshes, and multi-display CUSTOM replay. Separate expected cache warm-up plateaus from monotonic growth using post-warm-up slopes for private bytes, Python traced allocations by owner, Qt object/resource counts where safely observable, GL texture/buffer counts, GDI/USER handles, child processes, and ThreadManager tasks. Capture explicit quiesce checkpoints after settings close and engine teardown. **Reward:** finds slow leaks before packaged long-idle use while avoiding destructive cache disablement. **Acceptance:** every increasing series names an owner/call path or is classified as bounded cache growth with a cap; teardown returns threads/tasks/children/GL resources to the documented baseline; no cache, artwork, shadow, or visualizer fidelity is removed to make the graph flatter.
- [ ] **P1, high reward: attribute observed UI paint spikes before optimizing widgets.** The new run records Reddit paint maxima of `63.54 ms` and `48.78 ms`, Reddit2 `32.58 ms`, Gmail `26.69 ms`, Media `22.88 ms`, and analogue Clock `22.77 ms`; ordinary values are much lower, so aggregate averages hide burst ownership. Extend the existing bounded widget profiler with cause labels such as startup reveal, content commit, transition repaint, clock tick, cache regeneration, and settings rebuild, plus accepted-update-to-paint latency where already observable. Correlate these events against compositor render/paint gaps rather than reducing content or styling. **Reward:** identifies whether expensive paints are cold-cache construction, repeated invalidation, or coincident UI work and can recover visible frame headroom without quality loss. **Acceptance:** reproduce at least one spike per affected family with a named cause; optimize only after an owner is proven; retain exact visual comparison renders and current update semantics.
- [ ] **P2, medium reward: deepen `--usage` ThreadManager ownership health without polling Qt.** The baseline sidecar records pool sizes, submitted/completed/failed totals, non-sampler active work, process threads, and child processes. Extend manager-owned bookkeeping with queued/cancelled tasks by category, oldest task age, recurring-task count, and callback backlog, then let `--usage` consume only immutable/copied snapshots. Pair this with existing stall attribution so a UI-thread stall can be correlated with task completion bursts without enumerating Qt widgets, consuming the lock-free latest-stats channel, or running stack collection on every frame. **Reward:** catches duplicate workers, stranded recurring tasks, and completion storms that currently appear only as DT spikes or shutdown symptoms. **Acceptance:** normal idle/playback/settings/teardown baselines are documented, snapshots remain internally consistent under completion races, and shutdown reaches zero owned work with no new locks on render or UI hot paths.
- [ ] **P2, medium reward: define hardware/profile comparison protocol.** Record build/profile, display resolution/DPR/refresh, transition/visualizer mode, instrumentation support, driver/GPU identity, and source/cache state alongside results; compare Normal and MC builds using the same authored workload. Use medians and high percentiles plus worst-event timelines, not a single average FPS. **Reward:** makes optimization rewards reproducible and prevents hardware or cache differences being mistaken for regressions. **Acceptance:** one command produces a sanitized report and raw bounded metrics, with no machine path, account identifier, API key, media title, Steam title, or source URL.
